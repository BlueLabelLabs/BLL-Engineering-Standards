Active for a conventional web application. Composes the server-side archetype for any separate backend.
**Applies when:** The solution is a conventional web application (not primarily an ML-training or pure-backend service). Composes the server-side pack for any separate backend.

The hard rules from this pack are numbered guidelines and live in the
[guidelines catalog](../guidelines/README.md). What follows is the soft half:
the defaults we reach for, and how to choose when they do not settle it.
## Decisions this archetype introduces

- frontend_framework · backend_split · web_hosting

## Preferences

- Frontend framework: **Next.js** by default; a plain **React SPA** when the app is simple enough.
- Backend split: a significant **LLM / ML component** → build a **separate FastAPI backend** (see the `server-side` pack); a **standard web app with no AI** → use the **Next.js backend** (API routes / server actions).
- Hosting: **Next.js → AWS ECS or Vercel; Azure → Azure Static Web Apps or Container Apps**. A plain React SPA is statically hosted (CloudFront/S3 on AWS).

## Selection guidance

- Decide the backend split by AI presence: any meaningful LLM/ML interaction → a separate FastAPI service (`server-side` pack); otherwise Next.js full-stack.
- The backend follows the `server-side` pack; data, auth, monitoring, and environments follow `universal-baseline`; the provider pack supplies the concrete hosting and managed services.
- Frontend conventions (TypeScript, Tailwind, TanStack Query, Vite) are below the architecture barrier — see `references/conventions/frontend.md`.
