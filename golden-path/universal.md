The hard rules from this pack are numbered guidelines and live in the
[guidelines catalog](../guidelines/README.md). What follows is the soft half:
the defaults we reach for, and how to choose when they do not settle it.
## Preferences

- Prefer managed services over self-hosted infrastructure unless a driver requires otherwise.
- Prefer a single well-bounded component over premature decomposition; split only when a driver justifies it.
- Prefer boring, widely-supported technology over novel choices for core paths.
- Observability: use **one** provider, chosen by fit — these are **alternatives, not complements**. **LangSmith** by default (its strength is LLM/agentic systems, which is most of our work); **Logfire** when LangSmith doesn't fit (e.g. a non-LLM app). Use a cloud-native **in-tenant** option (Azure Application Insights / AWS CloudWatch) only when the client requires logging stay in their tenant, or a regulated regime calls for it.
- CI/CD: **GitHub Actions** by default; use the client's pipeline (e.g. Azure DevOps) only when they require it.
- Data: default relational store is **PostgreSQL** (use **SQL Server** when the client is a Windows shop). When modeling new data, consider a document store (**MongoDB Atlas**, in BlueLabel's managed Atlas account) first, but move to relational at the **first hint of relational structure** — don't force relational data into a document model. **No caching by default** — add it only when specifically required. (Provider packs name the concrete managed services.)
- Transactional email: default to **Mailgun**. **Never use AWS SES.**
- Local dev & packaging: every project ships with **Docker + docker-compose + a Makefile** exposing a standard command set — `make up`, `make down`, `make restart` (plus `build`, `logs`, `test`) — identical across repos, so any engineer runs any project the same way.
- Versioning: released apps use **SemVer `X.Y.Z`** — increment **MAJOR** for breaking changes, **MINOR** for backward-compatible features, **PATCH** for backward-compatible fixes; tag releases in git.
- Secret management has **three distinct jobs, one tool each**: **Passbolt** is the store of record for human-held credentials (entries named `BL###/Project/Credential`); **Doppler** is for one-time transport of a credential to a person, and is *never* a store of record; **the cloud secrets manager** (Key Vault / AWS Secrets Manager) is what the application reads at runtime. `.env` files are **gitignored and never committed**, and no secret lives in the repo in any form.
- API + MCP: any project that exposes an API also scaffolds a companion **MCP server** around it, using the **same authentication provider** as the main API.

## Selection guidance

- Reach for a new system element (service, datastore, external dependency) only when a driver justifies it; record the driver.
- When two options are comparable, prefer the one the team already knows (team-skills driver).
- Monitoring **approach** is chosen by *what is being built*, not by the cloud, and is independent of the host mechanism: use **active health-endpoint probing** (synthetic checks + latency thresholds, alerting on degradation, not just hard outages) for live request/response services (APIs, chatbots, agentic services); use **log/event-based monitoring** for batch jobs and data pipelines. The host **mechanism** is provider-specific — see the provider packs.

## Authentication & authorization

- End-user identity: default to **Auth0 or Firebase** — cloud-agnostic, **independent of the deployment cloud**. Use **Microsoft Entra ID only when the client's own workforce identity is already Entra, or they require their IdP** — *not* merely because the app is hosted on Azure. **Never use AWS Cognito.**
- We generally **build our own auth** rather than always federating; when a client requires SSO with their existing IdP, **federate via OIDC/SAML** (Auth0/Firebase can broker it).
- Authorization is **RBAC** — we do not go finer (no ABAC / policy engines). Roles and permissions live in the **application's own database**, not in IdP claims.
- API authentication: user requests use **JWT bearer tokens** issued by the IdP and validated at the API; machine-to-API access uses **OAuth2 client-credentials**. Tokens are **short-lived access + refresh** (exact lifetimes per the IdP).
- **MFA is enabled by default** (via the IdP).
- Multi-tenancy is not a standard concern; design for it only when a project genuinely requires it.
- Service-to-service / machine identity is **provider-native** — Managed Identity on Azure, IAM roles on AWS (see the provider packs) — distinct from end-user auth above.
