## Preferences

- Model access: default to **Azure AI Foundry** (most clients have an Azure deployment); use the **OpenAI API** directly when there is no Azure requirement.
- Models: **tailor the model to the task** rather than fixing one. Embeddings default to **OpenAI `text-embedding-3-large`**.
- Orchestration: **LangGraph** as the starting orchestration layer — even for simple RAG chatbots; it scales to multi-step, stateful, multi-tool agents without re-platforming.
- Retrieval store: start with **pgvector**; move to a specialized vector store only when a specific requirement demands it.
- Retrieval quality: **hybrid retrieval (semantic + keyword) and reranking are the default**, not add-ons.
- Prompt management & versioning: **PromptLayer or LangSmith** — pick one (alternatives, not both). Note **LangSmith** also covers observability and evals, so when LangSmith is the observability choice, use it for prompts/evals too rather than adding PromptLayer on top.
- Observability / tracing: **LangSmith** by default; **Logfire** where LangSmith doesn't fit.
- Cost: prompt caching; route cheap tasks (e.g. classification) to smaller models; token budgets.

## Selection guidance

- Model access: Azure AI Foundry when the client is on Azure (the common case); OpenAI API when unconstrained; a client-mandated AWS/GCP deployment → the provider-native model service (composes with the provider pack).
- Choosing a model: pick per task (reasoning vs. cheap classification vs. vision); pull a specific model from **HuggingFace** when off-the-shelf APIs don't cover the need. (Image detection / computer vision → see the `ml-training` pack: **YOLO** as a starting point.)
- **Non-text / multimodal ingestion is a required up-front decision** for any RAG system — decide before building, not later. It is chosen case by case; but for OCR / document parsing, **prefer native multimodal-LLM calls or a service such as LlamaParse — do NOT use Azure Document Intelligence.**
- For a multimodal corpus (images, schematics, scanned PDFs), **flag multimodal retrieval quality as the top technical risk to validate early** — whether the system reliably retrieves the right visual content is the make-or-break unknown, so always surface it as a key open question / first thing to prove.
- Retrieval scale-up: pgvector + hybrid + reranking first; reach for a managed/specialized store (Azure AI Search, Pinecone) only when scale or a specific requirement demands it.
- Recommended artifacts: agent/tool topology, RAG/retrieval data-flow, prompt inventory, eval-harness spec, guardrails/safety spec.
- Composes with provider + compliance packs: model access follows the provider; PII/PHI handling and logging tighten under compliance.
- A custom GPT / off-the-shelf assistant is a useful throwaway quick-win to surface real query patterns before building the full pipeline.
- Monitoring approach: a live agentic/chatbot service uses **active health-probing** — a health endpoint plus a synthetic round-trip (e.g. a monitor RAG query) with latency thresholds, alerting on degradation. (The host mechanism is provider-specific — see the provider pack.)
