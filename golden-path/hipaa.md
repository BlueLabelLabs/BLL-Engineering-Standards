**Applies when:** The project handles protected health information (PHI) or is otherwise in HIPAA scope.

The hard rules from this pack are numbered guidelines and live in the

the defaults we reach for, and how to choose when they do not settle it.
## Preferences

- Prefer first-party / BAA-covered managed services over third-party services for any path that touches PHI.
- Prefer network isolation (private subnets/endpoints) as the default posture, opening access deliberately.
- Observability: keep logging **in-tenant** — lean to Azure Application Insights over external SaaS observability (LangSmith/Logfire) for any path touching PHI (tightens the universal LangSmith+Logfire default).

## Selection guidance

- When a provider preference conflicts with a HIPAA invariant, the HIPAA invariant tightens it (composition: union-and-tighten).
- If a desired third-party service has no BAA, treat it as unavailable for PHI paths and find a covered alternative.

## Recommended baseline (HIPAA best-practice starting points — confirm and tailor per engagement)

Generally-accepted controls to start from (not BlueLabel-specific commitments):
- **No real PHI in non-production** — dev/test/staging use de-identified or synthetic data.
- **Access control**: least-privilege, role-based access to PHI; unique user identities; automatic session timeout / log-off; periodic access reviews.
- **Audit logging**: comprehensive and tamper-evident logging of PHI access (who/what/when), reviewed regularly, retained per the BAA.
- **Retention & disposal**: defined PHI retention periods and secure disposal (e.g. crypto-shredding) at end of life.
- **Backups & DR**: encrypted backups with tested restores; documented business-continuity / disaster-recovery.
- **Breach readiness**: an incident-response plan and breach-notification procedures (HIPAA's 60-day rule).
- **BAA register**: an inventory of every vendor/subprocessor touching PHI, each under a signed BAA.
- **Periodic security risk assessment.**
