## Stack
- **TypeScript** throughout.
- Styling: **Tailwind**.

## Testing
- UI tests: **Playwright**.
- When developing with an agent, author and exercise UI tests through the **Playwright MCP** server — the agent runs what it writes rather than assuming it works.
- Complete end-to-end journeys are verified through a **real browser against a running environment**, driven by **Claude Code's Chrome integration**. That is a development and pre-release check, not a CI step; the Playwright suite is what runs in CI.
- A flaky test is fixed or deleted. Retrying until green is not a fix.

## SQL / relational data standards

Engineering conventions for relational databases (**PostgreSQL** and **SQL Server**). These sit **below the architecture barrier** — they are data-modeling and build-time standards, not architecture decisions the architect chooses during the design walk. They are applied when *building*. The one genuinely architectural rule — **auditability** — lives as an invariant in `universal-baseline`.

## Modeling
- **Normalize by default.** Denormalize only for a specific performance or concurrency reason, recorded with the decision.

## Keys & columns
- Primary keys: **BIGINT identity / auto-increment** surrogate keys.
- Naming: **snake_case**; table names **singular**.
- Every table has **`created_at` and `updated_at`** — DB-enforced on create/modify, never set by the caller (see the auditability invariant).
- **Soft-delete by default** (do not hard-delete).

## Indexing
- The primary key has a **clustered index**.
- **Every query must be supported by an index** — no unindexed query paths.

## Data types
- No fixed type rules, with one exception: **never use `nvarchar(max)`** (SQL Server) — it cannot be indexed.
- **Never store binary data in the database.**
- **JSON** columns are acceptable, but prefer **normalizing** into the schema.
- **Never use XML columns.**

## Migrations
- **Versioned migrations**, checked into the repo, applied via CI/CD.
- Tooling: **Alembic** (Python / FastAPI) and **Entity Framework migrations** (SQL Server / .NET).

## Logic, connections, integrity
- **Stored procedures are acceptable** for business logic.
- Use **standard connection pooling**.
- **Foreign keys and constraints are always enforced in the database** — not app-level only.

## Auditing (PostgreSQL)
- **Row-level auditing via triggers** → an audit table that can trace every modification back. `created_at`/`updated_at` are DB-enforced. (This is the architectural rule — also stated as an invariant in `universal-baseline`.)
