## Preferences

- Compute: **ECS behind an ALB** (Fargate or EC2 launch type) for services; **Lambda** for event-driven glue and **EventBridge-scheduled** jobs. (No EKS — BlueLabel does not use Kubernetes; see `universal-baseline`.)
- Relational data: **Amazon RDS for PostgreSQL** (or **Aurora PostgreSQL**); **RDS for SQL Server** for Windows shops; **PostGIS** for geospatial. (Document-vs-relational stance per `universal-baseline`.)
- Document data: **MongoDB Atlas**, in BlueLabel's managed Atlas account (see `universal-baseline`).
- Caching: **none by default** — **ElastiCache** only when specifically required.
- Analytics / warehousing: not a standard — rarely needed; no default (BlueLabel rarely builds analytics/warehousing on AWS).
- Object storage: **Amazon S3**.
- Async messaging: **Amazon SQS** — keep it simple (no SNS/EventBridge messaging bus). No Kinesis / streaming.
- Container registry: **Amazon ECR**.
- CI/CD: **GitHub Actions**, per `universal-baseline`. **CodePipeline + CodeBuild + CodeDeploy is legacy** — retained on existing AWS projects that already run it, never chosen for new work. (Terraform still provisions infrastructure either way.)
- Environment isolation: development / staging / production live in **separate AWS accounts** (sub-organizations under AWS Organizations).
- Frontend: **React frontends are statically hosted on CloudFront** (S3 + CloudFront); backend on ECS/ALB. **CloudFront** is the CDN.
- Model access (agentic): the **OpenAI API endpoint** (the non-Azure default, per the `agentic-system` pack).
- In-tenant observability option: **Amazon CloudWatch** — only when the client requires logging stay in their AWS account, or under a regulated regime (default observability is LangSmith + Logfire, per `universal-baseline`).

## Selection guidance

- Compute: ECS (Fargate or EC2) behind an ALB for services; Lambda for events and scheduled jobs. Never EKS.
- Networking: VPC private subnets for app + DB; RDS not publicly accessible; security groups restrict access. **AWS WAF only if the client asks or the need arises**; CloudFront as the CDN (and static host for React frontends).
- Vector store (agentic): pgvector on RDS Postgres for modest scale; OpenSearch (or a managed vector DB) only when scale/hybrid requirements demand it.
- Observability: LangSmith by default, Logfire when it doesn't fit (one or the other, per universal); CloudWatch only for in-tenant/regulated logging.

## Monitoring host mechanism (AWS)

How a health monitor is *hosted and run* on AWS — independent of the monitoring **approach**, which is workload-driven (see `universal-baseline`).
- Host the monitor as a **Lambda** that reads config from **Secrets Manager**, persists its own state in **SSM Parameter Store** (decoupled from the app's datastore so the monitor survives an app-DB outage), and posts to a **Slack incoming webhook**.
- Trigger follows the chosen approach: an **EventBridge schedule** (e.g. `rate(5 minutes)`) for scheduled active probing; an event trigger for log/event-driven monitoring.
- Safety net: a **CloudWatch alarm** on the monitor Lambda's own `Errors` metric → **SNS → AWS Chatbot** posts to the same Slack channel, so the monitor failing still alerts.
