## Preferences

- Compute: **Azure App Service** for a single web/API app; **Azure Container Apps** for containerized or multi-service workloads; **Azure Functions** for event-driven glue and timer/scheduled jobs. **Never AKS / Kubernetes** — nothing we build is that complex.
- Relational data: **Azure Database for PostgreSQL (Flexible Server)** by default; **Azure SQL (SQL Server)** when the client is a Windows shop. **PostGIS** for geospatial.
- Document data: **MongoDB Atlas**, in BlueLabel's managed Atlas account (see `universal-baseline`; see selection guidance for the document-vs-relational stance).
- Caching: **none by default** — add **Azure Cache for Redis** only when specifically required (do not design caching up front).
- Analytics / BI: **Microsoft Fabric**.
- Object storage: **Azure Blob Storage**.
- Async messaging: **Service Bus** (ordered/transactional), **Event Grid** (reactive/fan-out), **Storage Queues** (simple decoupling). No Event Hubs / streaming — we don't need it.
- Container registry: **Azure Container Registry (ACR)**.
- Environment isolation: development / staging / production live in **separate resource groups**.
- Model access (agentic): **Azure AI Foundry** (composes with the agentic-system pack).
- In-tenant observability option: **Azure Application Insights** — used only when the client requires logging stay in their tenant, or under a regulated regime (default observability is LangSmith + Logfire, per `universal-baseline`).

## Selection guidance

- Compute: App Service for one managed web/API app; Container Apps for containerized/multi-service; Azure Functions for events and scheduled jobs. Never reach for AKS.
- Data modeling stance: consider a **document store (Mongo Atlas) first**, but move to **relational** (Postgres, or Azure SQL for Windows shops) at the **first hint of relational structure** — don't force relational data into documents.
- Networking: application servers and databases in private subnets; no public database endpoint (IP-restricted firewall only as a fallback). **Azure Front Door / Application Gateway are decided per project** — not a standard.
- Vector store (agentic): pgvector on the existing Postgres for modest scale; Azure AI Search for managed hybrid retrieval (good for heterogeneous/multimodal corpora).
- Observability: LangSmith by default, Logfire when it doesn't fit (one or the other, per universal); Application Insights only when in-tenant logging is required or for regulated industries (composes with the compliance pack).

## Monitoring host mechanism (Azure)

How a health monitor is *hosted and run* on Azure — independent of the monitoring **approach**, which is workload-driven (see `universal-baseline`).
- Host the monitor as an **Azure Function**, reading config from Application Settings (secrets from Key Vault) and posting to a **Slack incoming webhook**.
- Trigger follows the chosen approach: **Event Grid** for event/log-driven monitoring; a **Timer** trigger for scheduled active probing.
